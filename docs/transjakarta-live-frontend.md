# Live Transjakarta frontend

Transjakarta is the landing view. With the live feature configured, bus positions display automatically; choosing a route is optional. No route selection shows viewport buses; selecting a Transjakarta route filters that corridor. Other operators suspend live data. The user can switch live display off for the session.

Bus badges show the GTFS route short name in the route colour. Tap/click a badge, or expand the accessible bus list, for fleet identity, destination, current/next stop and receipt age. Coordinates with uncertain device time are labelled accordingly. This frontend does not calculate ETAs or infer occupancy.

## Required service

The browser consumes **SSE**, not MQTT. The MQTT listener is a separate long-running Node process (`live/`, started with `npm run live`) shipped in this branch. The Next.js frontend does not start it automatically, so a frontend-only deployment shows no live positions. The full setup, VPS and supervision runbook is [transjakarta-live.md](transjakarta-live.md).

Set before starting dev or building the frontend:

```dotenv
NEXT_PUBLIC_LIVE_ENABLED=true
# Empty for a same-origin reverse proxy serving /live/; local example:
NEXT_PUBLIC_LIVE_BASE_URL=http://127.0.0.1:8787
```

Flags are disabled in the example environment because service setup and realtime reuse terms must be resolved separately. Once enabled, the user-facing live toggle starts on. `NEXT_PUBLIC_` settings are embedded at build time.

## SSE contract

The service must accept one bounded scope:

```text
GET /live/vehicles?route=<known-gtfs-route-id>
GET /live/vehicles?bbox=<west,south,east,north>
```

No unrestricted fleet endpoint is needed. Send `Content-Type: text/event-stream`, `Cache-Control: no-store`, disable proxy buffering, and periodically emit:

```text
event: snapshot
data: {"scopeKey":"route=1","routeId":"1","status":"live","serverTime":1800000000000,"vehicles":[]}

```

`scopeKey` must exactly match the request query generated by `utils/live-scope.ts`. For bbox requests, `routeId` is null. A snapshot replaces the current scope's complete state, so omitted/expired vehicles disappear. State definitions and vehicle fields are in `utils/types/live.ts`. `status` is connecting/live/reconnecting/disconnected; report live only after a successful upstream subscription, not merely HTTP acceptance.

Each vehicle has validated raw/snapped coordinates, routeId/routeShortName/routeColor/routeTextColor derived from GTFS, identity, headsign, currentStop/nextStop, receivedAt, sourceTimestamp, clockOffsetMs and clock classification. Colours must be #RRGGBB. The client rejects invalid positions/styles and mismatched scope data. Never send credentials, guest tokens or full upstream payloads to the frontend.

The browser computes receipt age from `serverTime - receivedAt` plus elapsed local time, not by comparing server epoch to the browser's wall clock. Elapsed time uses both monotonic and wall clocks so system sleep expires old observations even if a browser pauses its monotonic clock. Uncorrected bus time is not the freshness oracle. Markers fade after30s and expire after90s without observation updates. Hidden tabs close SSE but keep the last positions in memory; on return they remain visible while reconnecting, with their original receipt ages advanced by the hidden interval. Empty connecting snapshots do not clear this cache; a live snapshot replaces it, including an empty one. Nothing is written to localStorage or a position-history store. Reconnect uses bounded backoff. Live updates must not modify camera bounds.

### Motion, and what it does not claim

Markers glide between fixes at a constant speed along **the shape of the bus's own trip**, so they follow the road through a turn instead of cutting across a block. The glide lasts about as long as that bus's measured interval between fixes, clamped to1-6 s. Consequences, stated plainly:

- **The marker trails the fix by up to about one interval.** It is never extrapolated ahead of the last observation, so a bus is never drawn where no data places it. The card's receipt age still describes the fix, not the glide.
- **A shape is used only when it clearly explains the move.** No shape, an observation more than30 m off the shape, projections that run backwards (opposite direction, or a loop the bus already passed), or a detour more than twice the straight distance (a different branch of a fork) all fall back to a straight glide. Shapes come from the static GTFS route detail, fetched on demand for visible routes only above zoom12; the selected route reuses the detail already on the page.
- **Motion is display-only and stops when it cannot be seen.** Below zoom12 the markers snap to each fix instead of animating, because a35 m move is under two pixels there. Reduced-motion users get snapped positions, hidden tabs stop animating, and stale or implausibly jumped fixes snap rather than crawl.
- **Heading is a claim, so an unknown heading is no arrow.** A missing heading hides the arrow; a stationary bus keeps its last confident heading rather than spinning at a halte; during a glide the arrow follows the road's local direction.
- Per-frame positions are written straight into the map source (a diff of only the buses that moved). React re-renders only when the set of buses, their badges, or their faded state changes.

## Verification

```bash
npx tsc --noEmit
npx tsx --test utils/*.test.ts
```

Browser checks completed with the separately implemented local listener: desktop1440x900 and touch390x844 land on Transjakarta with live already enabled, receive multi-route bbox snapshots, update scope on pan, filter to route1 on selection, open cards inside the viewport, keep explicit opt-out across route changes, and leave settled camera unchanged. No runtime/console errors observed. No screenshots required.

The official CC BY4.0 licence explicitly names GTFS Static. It must not be presented as a licence for realtime MQTT data; public availability alone does not establish redistribution rights. No listener or public deployment is started by this commit.
